## 0. 프로젝트 `dist` 와 서버 `www` (폴더 이름이 다른 이유)



- 로컬에서 `npm run build` 하면 Vite가 결과물을 **`dist/`** 아래에 만든다. 이 이름은 **도구 기본값**일 뿐이고, 서버에도 `dist` 라는 디렉터리가 있어야 하는 것은 **아니다**.

- 호스팅/서버에서는 보통 **`www`**, **`public_html`**, **`htdocs`** 등이 **웹 루트**(DocumentRoot)다. 배포할 때는 **`dist/` 안의 내용 전체**를 그 웹 루트로 **복사·동기화**하면 된다.

- 문서에서 **`dist/index.html`** 이라고 하면 “빌드 결과물 안의 `index.html`”을 뜻한다. 서버에서는 **`www/index.html`** (또는 실제 DocumentRoot 기준의 `index.html`)이 같은 파일이 되도록 올리면 된다.

- PHP API(`api/...`)도 레포에 `public/api` 또는 `dist/api`로 두는 경우가 있는데, 운영 서버에서는 **`www/api`** 처럼 웹에서 `/api` 로 접히는 경로에 맞추면 된다(호스팅 구조에 따름).

### 1.8 관리자 입점 목록 API — `get_applications.php` + `AdminApplications.jsx`



**① 반영할 파일 (로컬 · 수정본 위치)**



- `public/api/applications/get_applications.php`

- `dist/api/applications/get_applications.php`  

  *(레포에 `dist/api` 를 배포 소스로 쓰는 경우 동일 내용 유지)*

- `src/pages/admin/AdminApplications.jsx`  

- **빌드 후:** `AdminApplications` 수정분은 `dist/assets/AdminApplications-*.js` 청크에 포함



**② 파일 위치 (FTP · 서버)**



- `www/api/applications/get_applications.php`

- `www/index.html` + `www/assets/` *(같은 빌드 세트 — 프론트 변경 시)*



**③ 설명**



- **역할:** 로그인 사용자 ID로 `users.role` 을 다시 읽어 `$role` 및 `$_SESSION['user_role']` 에 반영. 세션만 오래된 값이면 관리자가 seller 분기로 가서 목록이 비거나 줄어듦.

- **관리자 쿼리:** `applications` 기준으로 `venues`·`users` 를 **`LEFT JOIN`**. 예전 `INNER JOIN` 은 연결 행이 없으면 해당 입점 신청 행 전체가 빠짐. 표시명은 `COALESCE(v.name, a.venue_name, …)`, `COALESCE(u.name, a.seller_name, …)` 등으로 `applications` 에 저장된 스냅샷도 활용.

- **화면:** `admin` / `superadmin` 일 때 페이지 마운트·역할 변경 시 `fetchApplications()` 를 한 번 더 호출해 목록 동기화.

- **주의:** 이 API는 **셀러→공간 입점 신청** 목록이다. 호스트 **공간 등록·승인 대기**는 `venues` 등 다른 흐름일 수 있음.

### 1.9 인증·입점 fetch 안정화 — `me.php` / `login.php` / `DataContext.jsx`



**① 반영할 파일 (로컬)**



- `public/api/auth/me.php` · `public/api/auth/login.php`

- `dist/api/auth/me.php` · `dist/api/auth/login.php` *(dist를 배포 소스로 쓰는 경우)*

- `src/context/DataContext.jsx` → **`npm run build`** 후 `dist/assets/index-*.js` 등에 포함



**② FTP**

- `www/index.html` + `www/assets/` *(프론트 변경 시 동일 빌드)*



**③ 설명**



- `me.php`·`login.php`: 사용자 조회 후 **`rowCount()` 대신 `fetch()` 결과**로 행 존재를 판별(MySQL PDO에서 SELECT `rowCount()` 가 0으로 나오는 환경 대비).

- `fetchApplications`: 응답을 **텍스트로 받아 `JSON.parse`**, 배열이 아니거나 HTTP 오류 시 **`setApplications([])`** 및 `console.warn` 으로 원인 추적 가능하게 함.

### 1.10 관리자 프로모션 API·화면 — `get_admin_promotions.php` 등



**① 반영할 파일 (로컬)**



- `public/api/promotions/get_admin_promotions.php`

- `public/api/promotions/set_promotion.php`

- `public/api/promotions/remove_promotion.php`

- `dist/api/promotions/` 위 세 파일 동일 *(dist 배포 시)*

- `src/pages/admin/AdminPromotions.jsx` → **`npm run build`** 후 `dist/assets/AdminPromotions-*.js`



**② FTP**



- `www/api/promotions/get_admin_promotions.php`

- `www/api/promotions/set_promotion.php`

- `www/api/promotions/remove_promotion.php`

- `www/index.html` + `www/assets/` *(프론트 변경 시)*



**③ 설명**



- 관리자 권한: **DB `users.role` 로 세션 동기화** 후 `admin` / `superadmin` 만 허용(`super_admin` 문자열 정규화 포함).

- 프로모션 목록: `venue_promotions` 기준 **`LEFT JOIN venues`** — 공간 행이 없어도 프로모션은 표시. 공간명은 **`venues.name` → `snapshot_venue_name`(컬럼) → `공간 #ID`** 순 `COALESCE`; 조인은 `CAST(TRIM(venue_id))` 보강. **`set_promotion`** 등록·수정 시 스냅샷 저장, **`get_admin_promotions`** 첫 로드 시 기존 행 **백필 UPDATE**(세션 `_vp_snapshot_backfill_2` 1회).

- 공간 선택 목록: **`approved` 만이 아니라 전체 공간** (`status` 컬럼 있으면 SELECT에 포함).

- 화면: API `success: false` 시 **토스트**로 메시지 표시.

## 2. 운영에 반영할 때 한 번에 정리



| 우선순위 | 로컬에서 손볼 것 | FTP(예: `www` 기준) |

|----------|------------------|----------------------|

| PHP | `public/api/...` 또는 `dist/api/...` | `www/api/...` 동일 상대 경로 |

| 입점 목록(관리자) | `public/api/applications/get_applications.php` *(필수)* | `www/api/applications/get_applications.php` |

| 인증 세션 | `public/api/auth/me.php`, `public/api/auth/login.php` | `www/api/auth/me.php`, `www/api/auth/login.php` |

| 관리자 프로모션 | `public/api/promotions/get_admin_promotions.php`, `set_promotion.php`, `remove_promotion.php` | `www/api/promotions/` 동명 |

| HTML·CSP | 루트 `index.html` 또는 빌드 후 `dist/index.html` | `www/index.html` |

| React 변경 | `src/**` 수정 후 **`npm run build`** | `www/index.html` + `www/assets/**` *(통째로 또는 해당 빌드 산출물)* |



### 권장 (배포 후 확인)



- Network: `get_notifications.php` → **200**, JSON.

- Console: `postcode.map.kakao.com` CSP 재발 여부.

- PHP 로그에 `[get_notifications]` 가 반복되면 DB/쿼리 추가 점검.

- 관리자 로그인 직후 입점 신청 **건수·목록**이 API와 맞는지.

- `GET .../api/applications/get_applications.php` (관리자 세션) → **200**, JSON 배열에 기대 행 포함. Network 응답이 비면 **PHP만 올리고 프론트는 이전 빌드**인지 확인.

## 3. 참고 (원인만 볼 때)



- **500**: `try` without `catch` 등 **PHP 구문 오류**로 실행 전 실패한 케이스.

- **CSP**: `frame-src` 에 `postcode.map.kakao.com` 미포함 시 iframe 차단.

- **입점 미반영**: 로그인 전 `fetchApplications` 가 401인 뒤, 로그인해도 **재요청 없으면** 목록이 빈 채로 남을 수 있음.

- **관리자 입점 목록 누락**: `$_SESSION['user_role']` 과 DB `users.role` 불일치 시 **seller 분기**; 관리자용 `INNER JOIN` 이면 **삭제된 venue/user** 가 있으면 해당 `applications` 행이 조회에서 빠짐.

- **프로필 완성도 67%**: 예전에는 6항목 중 **사업자 칸을 `business_no`만** 본 경우가 많음. **`profile_image`** 가 DB에 없으면 한 칸이 비어 **83%** 이하로 남을 수 있음.
